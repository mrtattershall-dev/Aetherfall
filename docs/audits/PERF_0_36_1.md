# Frame pacing and load, measured — 0.36.1

Headless Chromium at the real 540×960 viewport, the engine's own rAF loop
running. **Not a device.** Handoff §7 stands: the phone is the only renderer
that counts.

## Frame pacing — locked

Real `requestAnimationFrame` deltas, 180 sampled frames per case after warmup:

| Case | p50 | p95 | max | frames > 20 ms |
|---|---|---|---|---|
| Overworld, walking (Rowan's Hold) | 16.7 | 16.8 | 16.8 | **0 / 180** |
| Overworld, walking (the Outwood) | 16.7 | 16.7 | 16.8 | **0 / 180** |
| Battle (the Custodian) | 16.7 | 16.8 | 16.8 | **0 / 180** |

Vsync-locked 60 fps in all three, with no tail at all.

## A spike I chased that was not there

An earlier pass drove `update()` + `draw()` in a **tight loop** and measured
p95 26 ms, max 51 ms, with a clean period: a ~25 ms frame every sixth frame,
44 of 270 over budget. It looked exactly like a walk-cycle hitch, and the
animation advances on a 6-frame cycle, which made the story fit.

It is an artifact of the harness. Driving canvas work in a `for` loop lets the
GPU pipeline batch and flush on its own schedule, so the flush cost lands on
whichever call triggers it. Under rAF — how the game actually runs — the same
scenes hold 16.7 ms flat.

**Measure the loop the game runs, not a loop you wrote to measure it.** The
tight-loop numbers were not wrong about total work; they were wrong about
*when* it happens, which is the only part a player feels.

## Load

| | |
|---|---|
| File | 2.74 MB, single document |
| DOMContentLoaded | 1.32 s |
| load event | 1.37 s |
| Atlas | 432 KB (base64 of a 512×2840 PNG) |
| Audio | 439 KB (base64 of one MP3) |

Desktop, local file, warm cache — the floor, not the number a player sees. Two
thirds of the document is base64, which costs about a third more bytes than the
binary it encodes. That is the price of one self-contained file that runs from
a phone's Files app with no server, which is a deliberate project constraint,
not an oversight.

## What is not measured

- **Anything on a device.** Touch latency, real decode time, thermal
  behaviour, and cellular load are all unknown from here.
- **The build does not measure itself.** `AF-R-942` / `AF.perf` is still a
  phantom symbol, recorded as such since 0.6.19. Nothing in the running game
  reports its own frame time, so a regression on a phone would be noticed by
  feel rather than by number.
